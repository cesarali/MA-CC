# Feature: per-model parameter profiles for the LLM runtime

**Date:** 2026-08-17 · **Status:** ready for an implementation agent · **Plan only — nothing implemented**

**Goal:** stop discovering per-model API quirks by hitting HTTP 400 in the middle of a run.
Probe each model once, record what it accepts, and have the runtime apply the right
parameters automatically when that model is selected.

**Scope:** `src/llm_pharmpy/harness/llm_runtime/` and its project-owned bridge
`src/llm_pharmpy/harness/llm/`. No changes to prompts, orchestration, or evaluation.

---

## Why

Selecting a model can fail at call time for reasons that have nothing to do with the
prompt. Observed on 2026-08-17 with the university provider:

```
HTTP 400
litellm.UnsupportedParamsError: gpt-5 models (including gpt-5-codex) don't support
temperature=0.0. Only temperature=1 is supported. For gpt-5.1, temperature is supported
when reasoning_effort='none'. To drop unsupported params set litellm.drop_params = True.
Received Model Group=microsoft/gpt-5.4-nano
```

The caller asked for `temperature=0.0` — a reasonable default for a reproducible
scientific loop — and the request was rejected outright. Probing the same endpoint by hand
showed the request succeeds unchanged once `temperature` is `1` or absent.

This will recur. The endpoint advertises 28 models spanning several families
(`gpt-4o`, `gpt-4.1`, `gpt-5.x`, `claude-*`, `gpt-image-*`), each with its own rules. Every
new model is currently a trial-and-error discovery, mid-run, after the prompt has already
been built.

The runtime already knows *which* models exist (`GET /models` during endpoint discovery)
and what they *cost* (`ModelPricing`). It does not know what parameters they accept.

---

## What exists today

| Concept | Where | Granularity |
|---|---|---|
| `ProviderCapabilities` | `providers/capabilities.py` | **provider**, static |
| `ModelPricing` | `providers/pricing.py` | **model** |
| Payload construction | `adapters/_openai_compatible.py::complete` | always sends `temperature` and `max_tokens` |
| `CompletionRequest` | `providers/requests.py` | `temperature: float = 0.0`, required and non-optional |

The gap is a **model**-level statement of accepted parameters. `ProviderCapabilities` is
the right shape but the wrong granularity; `ModelPricing` proves per-model records already
belong in this layer.

---

## Design

### 1. `ModelProfile` — the record

Add `providers/model_profiles.py`.

```python
@dataclass(frozen=True)
class ModelProfile:
    provider_type: str                      # "university", "openai", …
    model: str                              # "microsoft/gpt-5.4-nano"
    family: str                             # "gpt-5", "gpt-4", "claude", "unknown"
    temperature: TemperatureRule            # see below
    supports_seed: bool | None = None       # None = not probed
    supports_system_messages: bool | None = None
    max_output_tokens_field: str = "max_tokens"
    probed_at: str | None = None            # UTC ISO-8601
    probe_source: str = "unprobed"          # "probe" | "manual" | "inferred"
    notes: tuple[str, ...] = ()
```

`TemperatureRule` must distinguish three genuinely different cases, because they need
different handling:

- `any` — any non-negative value is accepted.
- `fixed(value)` — only this exact value is accepted; anything else is a hard 400.
- `omit` — the parameter must not be sent at all.

Do not collapse `fixed(1.0)` and `omit`. They look identical for gpt-5 today but are
different contracts, and a probe can tell them apart.

### 2. `ModelProfileRegistry` — lookup with honest fallback

```python
class ModelProfileRegistry:
    def get(self, provider_type: str, model: str) -> ModelProfile: ...
    def known(self) -> tuple[ModelProfile, ...]: ...
```

Lookup order: exact `(provider_type, model)` → family rule inferred from the model name →
a permissive default marked `probe_source="inferred"`.

**An inferred profile must be visibly inferred.** A caller reading a profile has to be able
to tell "we tested this" from "we guessed". Guessing wrong is exactly today's failure, and
silently presenting a guess as knowledge would make it worse.

Ship a checked-in catalogue at `providers/model_profiles.json`, generated by the probe and
loaded at import. It is data, not code, so updating it is a data change reviewable in a
diff.

### 3. Where the rule is applied — the important decision

`llm_runtime` is **vendored** from `mas_cc` (see `VENDORED_FROM.md`); permanent generic
changes belong upstream first. But `_openai_compatible.complete()` builds the payload
internally, so it looks like the natural place to consult the registry.

**Do not modify the vendored adapter.** `temperature` and `seed` are fields on
`CompletionRequest`, so the rule can be applied *before* the request reaches the provider:

```python
# harness/llm/ — project-owned
def apply_model_profile(request: CompletionRequest, profile: ModelProfile) -> CompletionRequest
```

Wrap provider construction in `harness/llm/factory.py` so every project caller gets the
normalization automatically. This needs no vendored divergence and no upstream round trip.

**Known limit, state it in the code:** a quirk that cannot be expressed as a
`CompletionRequest` field — for example a model requiring `max_completion_tokens` instead
of `max_tokens` — cannot be fixed this way, because that field name is chosen inside the
adapter. Record such a model as **unsupported** with a clear message rather than silently
failing. Today's probe found `gpt-5.4-nano` accepts both spellings, so this is not yet
blocking; if it becomes blocking, that is the trigger for an upstream change, and the
`ModelProfile.max_output_tokens_field` field exists to carry the information when it does.

Applying the rule must also be **loud when it overrides the caller**. If a caller asks for
`temperature=0.0` on a `fixed(1.0)` model, the request is silently non-reproducible unless
something says so. Record the substitution in the response metadata or emit a warning once
per (model, rule) pair — never adjust in silence.

### 4. The probe script

`scripts/exploratory/llm_providers/probe_model_parameters.py`

Two phases, matching how the list gets curated:

**Phase 1 — list.** `--list-models` calls `GET /models`, writes every advertised model to a
plain text file, one per line, sorted:

```bash
uv run python scripts/exploratory/llm_providers/probe_model_parameters.py \
    --provider university --list-models configs/llm/university_models.txt
```

The user then deletes the lines they do not care about. Comments (`#`) and blank lines are
ignored, so entries can be commented out rather than lost.

**Phase 2 — probe.** `--models-file` probes only the surviving entries:

```bash
uv run python scripts/exploratory/llm_providers/probe_model_parameters.py \
    --provider university --models-file configs/llm/university_models.txt \
    --output src/llm_pharmpy/harness/llm_runtime/providers/model_profiles.json
```

For each model, send a minimal request (`"hi"`, 16 output tokens) under each variant and
record the status and any error text:

| Variant | Determines |
|---|---|
| `temperature=0.0` | whether an arbitrary temperature is accepted |
| `temperature=1.0` | whether the fixed value is accepted |
| temperature omitted | whether `omit` is required rather than `fixed` |
| `seed=7` | `supports_seed` |
| system + user messages | `supports_system_messages` |
| `max_tokens` vs `max_completion_tokens` | `max_output_tokens_field` |

Derive `TemperatureRule` from the results: `0.0` accepted → `any`; only `1.0` accepted →
`fixed(1.0)`; only omission accepted → `omit`.

Rules the script must follow:

- **Never print or write the API key**, including inside captured error text — scrub before
  recording.
- Keep each probe minimal. A rejected request is not billed; a successful one costs a few
  tokens. Report the total number of successful calls at the end so cost is visible.
- Real network calls require explicit opt-in (`--confirm-live-calls`); without it, print
  the plan and exit.
- Treat every failure as data. A model that errors for an unrelated reason (image-only
  models such as `gpt-image-1.5` will) is recorded as unsupported with its message, not a
  crash.
- Write output atomically and keep entries sorted, so the JSON diffs cleanly.
- Preserve existing entries for models absent from this run rather than dropping them.

`potsdam_wsl_bridge/*.ps1` does — otherwise it vanishes in an installed wheel.

## Tests

No test may make a network call. Probe results are fixtures.

| Test | Proves |
|---|---|
| Exact lookup returns the checked-in profile | the catalogue loads |
| Unknown model returns a profile marked `inferred`, never `probe` | guesses are labelled |
| `fixed(1.0)` rewrites `temperature=0.0` to `1.0` | the fix works |
| `omit` produces a request the adapter sends without temperature | `omit` ≠ `fixed` |
| `any` leaves the request untouched | no gratuitous rewriting |
| An override is recorded/warned, not silent | reproducibility loss is visible |
| A model with `supports_seed=False` has its seed dropped | seed handling |
| Round trip: `ModelProfile` → JSON → `ModelProfile` | catalogue integrity |
| Every entry in the shipped JSON parses and names a known provider type | no rot |
| Probe result parsing: 400-with-litellm-text → `fixed(1.0)`; all-succeed → `any` | derivation logic |
| A built wheel contains `model_profiles.json` | packaging, as for the `.ps1` |

Test the probe's **derivation logic** against recorded HTTP responses as fixtures. Include
the verbatim `litellm.UnsupportedParamsError` text from this session as one fixture — that
string is the exact real-world input the parser must handle.

## Implementation order

1. `ModelProfile`, `TemperatureRule`, `ModelProfileRegistry`, and a hand-written JSON with
   two entries (one gpt-5, one gpt-4o). Tests for lookup and fallback labelling.
2. `apply_model_profile` plus factory wiring, and the override-visibility rule. Tests.
3. The probe script's list phase, then its derivation logic against fixtures — no live
   calls yet.
4. Live probe behind `--confirm-live-calls`; generate the real catalogue for the models the
   user keeps in `configs/llm/university_models.txt`.
5. Remove the `--temperature 1.0` workaround from the two evolution scripts.
6. Package data, wheel check, `VENDORED_FROM.md` note, full suite and Ruff.

---

## Done when

- Selecting any model in the curated list and issuing a normal request succeeds without the
  caller knowing that model's quirks.
- A model whose constraint cannot be satisfied is reported clearly **before** the call, not
  as an HTTP 400 mid-run.
- Every automatic override is visible to the caller.
- Profiles state whether they were probed or inferred.
- Re-running the probe updates the catalogue as a clean, sorted diff.
- No vendored file changed except `VENDORED_FROM.md`.
- Local suite and Ruff pass; no test touches the network.

## Out of scope

Pricing (already covered by `ModelPricing`), streaming, tool/function-call differences,
`response_format`/JSON mode, `reasoning_effort`, image models beyond marking them
unsupported, automatic model selection or fallback chains, and any change to prompt
versions or the evolution loop.

## Notes for the implementing agent

- The endpoint is a **litellm** proxy. Its errors are unusually descriptive and name the
  rule directly — parse them, but never depend on the exact wording for control flow; treat
  the observed status code as the ground truth and the text as a recorded note.
- `GET /models` needs no special handling: endpoint discovery in `_openai_compatible.py`
  already resolves whether the path carries a `/v1` prefix. Reuse it rather than
  reimplementing.
- The university provider requires the WSL bridge under WSL; it starts automatically via
  `llm_runtime/potsdam_wsl_bridge`. A live probe therefore needs the Windows VPN connected.
- Evidence and context for the original failure:
  [rendered prompt](../../documentation/pharma_evolve/17082026_evolution_prompt_v3_minimal.md),
  [university API notes](../../documentation/llm/university_llm_api.md).
